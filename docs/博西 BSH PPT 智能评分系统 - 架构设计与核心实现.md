# 博西 BSH PPT 智能评分系统 — 架构设计与核心实现

---

## 一、项目业务背景

面向博西内部技术评审场景，员工上传 PPT（可配套演讲音频），系统通过多模型协作实现自动化质量评审：

- **视觉层**：通义千问 VL 视觉模型逐页分析幻灯片内容
- **语音层**：AssemblyAI 转录音频并提取语音指标（语速、停顿、口头禅）
- **评分层**：大模型从"结构与逻辑"、"内容与价值"、"语言与呈现"三个维度并行评分
- **输出层**：自动生成 PDF 评审报告，替代人工逐页审阅的低效流程，实现技术分享质量标准化

## 二、核心约束与整体架构

### 2.1 核心瓶颈约束

百炼 API 配额按主账号维度计算：

| 模型         | 每分钟请求数（RPM） | 等效 QPS                      | 用途               |
| ------------ | ------------------- | ----------------------------- | ------------------ |
| qwen-vl-plus | 60                  | **1 QPS** ← 全系统瓶颈 | 逐页视觉分析       |
| qwen3-max    | 1,200               | 20 QPS                        | 分类 + 评分 + 汇总 |
| AssemblyAI   | 200 并发            | 非瓶颈                        | 音频转录           |

VL 是唯一瓶颈：一份 20 页 PPT 需要 20 次 VL 调用，在 1 QPS 下最少耗时 20 秒。全系统所有架构设计均以"不突破 VL 1 QPS"为核心约束展开。

此外，百炼同时有 TPM（Token 消耗）限流：VL 为 100,000/分钟，LLM 为 1,000,000/分钟。客户端无法精确预计算 Token 用量（VL 图片 token 由服务端编码、LLM 输出 token 不可预测），因此不做 TPM 令牌桶，以 RPM 限流为主控面——RPM 限流到位，正常请求不会触发 TPM 上限；万一超标收到 `Allocated quota exceeded`，由熔断降级链路兜底。


### 2.2 三段式拆分设计思路

将完整评分流水线拆分为三个独立阶段，通过任务队列解耦，消除串行流程的资源空转：

| Worker       | 队列            | 并发数       | 职责                      | 约束                         |
| ------------ | --------------- | ------------ | ------------------------- | ---------------------------- |
| VL Worker    | `vl_tasks`    | **1**  | PPT 预处理 + 逐页视觉分析 | 1 QPS 物理上限，严格串行     |
| Audio Worker | `audio_tasks` | **5**  | AssemblyAI 音频转录       | 200 并发配额，与 VL 并行执行 |
| LLM Worker   | `llm_tasks`   | **20** | 分类 + 三维度评分 + 汇总  | 20 QPS 配额，真正并行        |

**三段衔接逻辑：** VL 段与 Audio 段并行执行（asyncio.gather），两路全部完成后通过 Celery chord（扇出→汇合）自动触发 LLM 段。不同用户的 VL 任务在同一队列先到先得——前一个用户 VL 结束，下一个用户 VL 立刻启动，无需等待前者的 LLM 阶段跑完，彻底消除资源空转。

**多用户并发执行时序（20 页 PPT 举例）：**

```
时间轴 →  0s      20s          25s         45s
─────────────────────────────────────────────────────
User A:   [VL×20页=20s]      [LLM⑤⑥⑦+报告=5s]
User B:          [VL×20页=20s]       [LLM⑤⑥⑦+报告=5s]
User C:                   [VL×20页=20s]       [LLM=5s]
```

A 的 LLM 评分和 B 的 VL 分析**同时运行**，互不阻塞。总吞吐：每 20 秒完成 1 个用户的 VL 分析，完全由 1 QPS 物理上限决定。


### 2.3 评分流水线全景（9 个阶段）

```
用户上传 PPT + 音频（可选）
    │
    ▼ [FastAPI 接入层：立即返回 task_id，不等待]
    │
    ▼ ① PPT → PDF（LibreOffice headless 转换）
    │
    ▼ ② PDF → PNG 截图（PyMuPDF，每页一张）
    │
    ▼ ③ 并行执行（asyncio.gather）
    │    ├─ 线路A：逐页调用 VL 分析视觉内容（Redis 令牌桶严格限速 1 QPS）
    │    └─ 线路B：音频转录（AssemblyAI，无需限速）
    │
    ▼ ④ 合并上下文 —— 纯内存操作
    │
    ▼ ⑤ 分类 LLM —— 判断 PPT 类型（产品创新/问题解决/降本增效/方法工具）
    │
    ▼ ⑥ 3 维度 LLM 并行评分（asyncio.gather）
    │    ├─ 维度A：结构与逻辑（含 thinking 推理链）
    │    ├─ 维度B：内容与价值（含 thinking 推理链）
    │    └─ 维度C：语言与呈现（仅有音频时）
    │
    ▼ ⑦ 汇总 LLM —— 生成 strengths/weaknesses/suggestions/summary
    │
    ▼ ⑧ 生成 PDF 报告（Markdown → Puppeteer → PDF）
    │
    ▼ ⑨ 入库（scoring_records）+ SSE 通知前端
```

**LLM JSON 多级容错解析：** 大模型返回的 JSON 经常被 Markdown 代码块包裹，或含非法控制字符——不能直接 `json.loads`。处理链路分四层：提取代码块后严格解析 → 清洗轻度控制字符（保留 `\t\n\r`）→ 清洗全部控制字符 → 兜底返回 `{}`。每层失败才进入下一层，不假设 LLM 永远输出合法 JSON。

**内容相关性门控（仅音频模式）：** 评分前先判断 PPT 主题与演讲内容是否相关。低相关（PPT 讲产品、演讲聊家常）直接强制技术性低分（满分 30%），不进入正常评分流程；中相关设分数上限（满分 75%）；高相关正常评分。防止"PPT 和演讲两张皮"拿到不应得的高分。

## 三、核心四板斧实现详解

### 3.1 板斧一：Redis 分布式令牌桶

#### 为什么选择令牌桶

| 算法             | 特点                                 | 问题                                                                                 |
| ---------------- | ------------------------------------ | ------------------------------------------------------------------------------------ |
| 计数器           | 实现最简单                           | 分钟边界产生流量突刺——第 59 秒和第 1 秒连续爆发两倍流量，直接触发平台秒级 RPS 保护 |
| 漏桶             | 严格匀速输出                         | 完全不允许突发，LLM 评分阶段无法一次性并行取 3 个令牌                                |
| 滑动窗口         | 精确统计，无突刺                     | 实现复杂，需维护多个子窗口计数，内存开销高                                           |
| **令牌桶** | **平均速率受控，允许可控突发** | **✅ 最适合 API 限速场景**                                                     |

令牌桶以固定速率（rate/s）生成令牌放入桶中，桶有容量上限（= rate），请求来时消耗令牌。既保证平均速率受控，又允许桶内积攒的令牌支持临时突发（如 3 个 LLM 维度同时取 3 个令牌）。正好匹配业务需求。

#### 实现方案：Redis + Lua 原子扣减

限流必须跨 Worker 全局共享才能保证不超配额。本地计数器各管各的，多 Worker 叠加必然突破上限。

但共享存储本身不够——"读令牌 → 判断够不够 → 扣减"是三步操作。如果拆为三条 Redis 命令（HGET → 判断 → HSET），两个 Worker 可能同时读到 `tokens=1`，各自判断够、各自扣——结果两个请求都发出去了，超发。

**Lua 脚本是解决这个问题的标准答案。** Redis 执行命令是单线程的，Lua 脚本被 Redis 当作一个不可分割的执行单元——整段"读 → 补 → 判 → 扣 → 写"一次性跑完，期间任何其他客户端的命令都不会插入。没有插队，就没有竞态条件，"读-判-扣"在 Lua 脚本里是不可分割的操作。

```lua
-- KEYS[1]: 令牌桶 Redis key
-- ARGV[1]: 速率 (rate)
-- ARGV[2]: 当前时间戳
-- ARGV[3]: 请求令牌数 (默认 1)

local key       = KEYS[1]
local rate      = tonumber(ARGV[1])
local now       = tonumber(ARGV[2])
local requested = tonumber(ARGV[3]) or 1

-- 读取当前状态
local last_time = tonumber(redis.call('HGET', key, 'last_time') or now)
local tokens    = tonumber(redis.call('HGET', key, 'tokens') or rate)

-- 按时间流逝补充令牌（elapsed 窗口上限 1 秒）
local elapsed = math.min(now - last_time, 1.0)
tokens = math.min(rate, tokens + elapsed * rate)

-- 判断 + 扣减
if tokens >= requested then
    tokens = tokens - requested
    redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, 3)
    return 1   -- 成功
else
    redis.call('HSET', key, 'last_time', now)
    redis.call('EXPIRE', key, 3)
    return 0   -- 失败
end
```

#### 三个关键设计决策

**elapsed 上限 1 秒。** 即使 Worker 停了 10 秒，也只补充 1 秒的令牌。防止空闲后令牌大量囤积，恢复时瞬间爆发触发百炼秒级 RPS 保护。

**桶容量 = rate。** bucket size 设得比 rate 大意味着空闲后可以囤积超出配额的令牌——囤积了就能在 1 秒内爆发出去，直接触发 429。所以桶容量必须等于 rate，等于说"不允许囤积"，从机制上杜绝秒级突发。

**失败也更新 last_time。** 拿不到令牌时同样刷新时间戳，避免重试请求反复计算 elapsed 重复补充令牌。

#### Python 侧封装

封装为 `async with` 上下文管理器——进入时轮询等待令牌，拿到才放行；退出时空操作，令牌已消费无需归还。业务代码零侵入：

```python
async with VL_RATE_LIMITER:
    result = call_vl_api()
```

#### 效果

1000 个协程同时争抢空桶，最多 1 个成功——Lua 原子性不依赖任何应用层锁，纯由 Redis 单线程执行模型保证。未来 Worker 从 1 个扩到 N 个，只需修改 rate 参数，无需改动核心逻辑。


### 3.2 板斧二：三段式任务队列（Celery + Redis）

#### 为什么要拆三段

不拆分时，全流程是一个大串行任务，带来两个严重问题：

1. **资源浪费**：VL 是瓶颈（1 QPS），LLM 配额富裕（20 QPS），但 VL 跑完前 LLM 全程空闲
2. **全局阻塞**：用户 A 在跑 LLM 时 VL Worker 空转，用户 B 完全无法开始，所有人都被卡住

拆分为三个独立队列后，不同用户的不同阶段可以重叠执行——用户 A 的 LLM 评分和用户 B 的 VL 分析同时进行，互不阻塞。吞吐完全由 VL 1 QPS 物理上限决定，无架构层面的额外浪费。

#### 三段衔接机制

VL 段与 Audio 段通过 `asyncio.gather` 并行启动，两路全部完成后，通过 Celery 的 **chord（扇出→汇合）** 机制自动回调触发 LLM 段。Worker 崩溃时任务自动回到队列头部，不会丢失。

#### 为什么选 Redis + Celery 而非 Kafka

| 维度       | Redis + Celery                                | Kafka                          |
| ---------- | --------------------------------------------- | ------------------------------ |
| 场景匹配   | ✅ 任务队列（每条消息只需一个消费者处理一次） | 事件流（同一条消息多下游消费） |
| 运维成本   | 低（Redis 已部署用于令牌桶、进度存储）        | 高（需独立部署 Kafka + KRaft） |
| 生态成熟度 | Python 异步任务最成熟方案，内置重试、结果回传 | Java 生态更强                  |
| 适合本项目 | ✅                                            | ❌ 过度设计                    |

当前是任务队列场景而非事件流场景——每条消息只需一个消费者处理一次，结果返回给提交任务的用户。Redis 本身已部署用于令牌桶和进度存储，零额外运维成本。后续若需审计日志、实时计费等多消费方场景，可追加 Redis → Kafka 链路，无需重构现有架构。

#### 底层原理

Celery 本质是基于 Redis List 实现的生产者-消费者模型：

- 生产者（FastAPI）：`LPUSH` 将任务推入队列左侧
- 消费者（Worker）：`BRPOP` 从队列右侧阻塞式弹出——空队列时 Worker 挂起不轮询，有任务进来立刻被唤醒

Redis 单线程特性天然保证不会出现"两个 Worker 同时弹出同一个任务"的竞争问题。

Celery 在朴素 List 之上提供了三项生产级能力：**任务路由**（多队列配置驱动，打标签即可路由到不同 Worker）、**结果回传**（task_id 查询执行结果）、**故障恢复**（`task_acks_late` + `max_retries`）。

#### 任务可靠性保障

- **task_acks_late=True**：Worker 执行完成才确认消费，中途崩溃任务自动回到队列头部
- **max_retries=3**：被限流 429 时自动重试，间隔 60 秒等待配额恢复
- **worker_max_tasks_per_child=50**：每 50 个任务重启子进程，防止依赖库内存泄漏累积


### 3.3 板斧三：业务幂等 + VL 断点续跑 + 单页缓存

三层保护从粗到细，逐层拦截重复调用与资源浪费。

#### 第一层：任务级业务幂等（内容哈希）

用户提交 PPT 时，对 PDF 文件原始字节计算 SHA256，拼接用户 ID 作为 key 去 Redis 查询：

- **命中**：直接返回已有 task_id 与报告链接，任务不进入队列，不消耗 VL 配额
- **未命中**：正常走流水线，完成后将 `{用户ID:文件SHA256} → task_id` 写入 Redis，TTL 与报告文件同步

基于文件内容而非文件名去重——同文件改名上传也会被拦截。使用 SHA256 而非 MD5，避免哈希碰撞风险。这层的价值是**挡在队列入口之前**，防止同一份 PPT 重复排队浪费 VL 资源。

#### 第二层：调用级 VL 断点续跑

VL 是串行瓶颈，20 页跑 20 秒。Worker 中途崩溃从头再来是不可接受的——已分析的 19 页耗费的 API 配额和等待时间全部白费。

每个任务在 Redis 维护两个数据结构：

- `task:{id}:pages_done`：**Set** 类型，存储已完成页码集合（如 `{1, 3, 5, 7}`）
- `task:{id}:pages`：**Hash** 类型，存储每页 VL 分析结果 JSON

Worker 每处理完一页，通过 **Redis Pipeline** 原子提交三连操作：`HSET`（存结果）→ `SADD`（标记完成）→ `EXPIRE`（设 24h TTL）。Worker 重启后先读 `pages_done` 拿到已完成页码集合。遍历所有页时，碰到已完成的直接从 Hash 取缓存结果跳过——从哪断的从哪续，已分析的页不重调 API。

#### Pipeline 与 Lua 脚本的区别

| 对比维度     | Pipeline                      | Lua 脚本                      |
| ------------ | ----------------------------- | ----------------------------- |
| 执行连续性   | ✅ 连续执行，无其他客户端插队 | ✅ 连续执行，无其他客户端插队 |
| 条件判断能力 | ❌ 仅支持无条件顺序执行       | ✅ 支持 if/else 分支逻辑      |
| 事务回滚能力 | ❌ 前序成功后序失败无法回滚   | ✅ 全或无的原子执行语义       |
| 适用场景     | 断点续跑批量写入（足够）      | 令牌桶判断+扣减（必须）       |

断点续跑只需无条件批量写入——不需要判断"够不够"再决定写不写。Pipeline 完全够用，无需引入 Lua 脚本增加复杂度。令牌桶必须判断 `tokens >= requested` 后才扣减，这就必须用 Lua。

#### 第三层：API 级单页缓存

VL 调用的输入只有两样：一张 base64 编码的图片 + 一段提示词文本。对两者拼接计算 **MD5**，存 Redis，key 为 `vl_cache:{哈希值}`，value 为 VL 返回的 JSON 字符串，TTL 72 小时。

每次调 VL API 前先查缓存——命中直接返回不消耗配额，未命中调 API 后回写缓存。

- **为什么用 MD5 不用 SHA256：** 缓存场景对碰撞容忍度高——万分之一概率撞了也只是把一页分析结果等同于另一页，评分最多偏一点，不会出安全问题。MD5 计算更快、key 更短，省 Redis 内存。
- **为什么能识别图片修改：** MD5 是对 base64 整个字符串算的。原图一个像素变了 → PNG 渲染不同 → base64 完全不同 → MD5 必然不同 → 缓存不命中。宁可偶尔多调一次 API 也不误判命中。
- **实际收益场景：** 同一 PPT 模板的封面页、目录页在团队内部被多份 PPT 复用，跨用户共享缓存，有效减少 API 调用量。


### 3.4 板斧四：熔断 + 多模型降级 + 多 Key 轮询

#### 四层防护协作关系

调用完整链路：**取 Key（轮询池）→ 拿令牌（令牌桶）→ 调 API → 成功返回 / 失败触发熔断降级**

每层各司其职：令牌桶做主动限流（防超配额），熔断器做被动保护（API 挂了不发无效请求），降级链做容灾（挂了也能出结果），Key 池做横向扩展（多账号叠加配额）。缺一层都不完整。

#### 熔断器状态机

不是简单的"出错就 sleep 60 秒重试"，而是标准的三级状态机：

```
CLOSED（正常态） ──(连续失败 ≥ 5次)──▶ OPEN（熔断态）
                                            │
                                    60s 冷却后 │
                                            ▼
                                     HALF-OPEN（半开探测态）
                                     只放行 1 个请求试探
                                    /              \
                              试探成功            试探失败
                              → CLOSED           → OPEN（重新熔断）
```

**核心设计：** 冷却结束后不是全量恢复，而是先放 1 个探路。成功 → 恢复正常；失败 → 继续熔断。万一 API 还没好，只浪费 1 次调用而不是全部撞墙。

OPEN 态下所有请求直接抛 `CircuitBreakerError`，不发起网络请求——省时间、省配额。

#### 多模型降级链

降级顺序有讲究：同 Key 模型优先（零额外成本），跨供应商其次（真正的容灾备用），兜底方案最末（保证服务可用）：

| 层级   | VL 降级        | LLM 降级    | 音频降级       | 特点                |
| ------ | -------------- | ----------- | -------------- | ------------------- |
| 主模型 | qwen-vl-plus   | qwen3-max   | AssemblyAI     | 默认                |
| 降级 1 | qwen3-vl-flash | qwen-turbo  | faster-whisper | 同 Key/本地，零成本 |
| 降级 2 | GLM-4V-Flash   | GLM-4-Flash | —             | 跨供应商容灾        |
| 兜底   | skip_image     | 友好提示    | 跳过音频       | 保证不崩溃          |

代码维护为一个有序列表，从头遍历找到第一个可用的。用户无感知切换。

#### 多 Key 轮询扩容

百炼配额按**主账号**独立计算——同一个主账号下所有 Key 共享 60 RPM，不同主账号间配额完全独立。团队成员的独立百炼账号各自有 60 RPM，跨主账号轮询即可线性叠加（前提：Key 来自不同主账号）。

代码维护 Key 池，Round-Robin 轮询派发。Key 收到 429 时自动标记禁用 + 冷却 60 秒，轮询时自动跳过。全部 Key 不可用时进入降级链兜底。

|                | VL 配额 | LLM 配额  | VL Worker 并发 |
| -------------- | ------- | --------- | -------------- |
| 1 个主账号     | 60 RPM  | 1,200 RPM | 1 并发         |
| 3 个主账号轮询 | 180 RPM | 3,600 RPM | 3 并发         |
| 5 个主账号轮询 | 300 RPM | 6,000 RPM | 5 并发         |

## 四、高可用配套设计

### 4.1 超时分层控制

**核心思路：** 接入层固定超时（与业务内容无关），执行层动态超时（根据实际工作量计算）。不是全局一刀切。

**接入层固定超时：** Nginx（10s）和 FastAPI（5s）只负责收文件、写 Redis、返回 task_id，跟 PPT 页数无关。操作本身 1 秒内完成，超时仅用于防御网络异常和磁盘故障。

**执行层动态超时：**

- **单次调用最坏值（压测确定）**：VL 单页 30s、LLM 单次 60s、音频转录 120s。通过压测拿到 P99 耗时加安全余量后写为常量，跟总页数无关——每页 VL 调一次 API，单次耗时分布不变。
- **任务总超时（动态计算）**：创建 Celery 任务时根据实际页数实时计算：

```
总超时 = 页数 × VL 单次最坏值
       + 分类 LLM（1次）
       + max(三维度并行耗时)   ← 并行取最长，不累加
       + 汇总 LLM（1次）
       + 音频耗时
       + 安全余量
```

页数在 PPT 转 PNG 时确定，LLM 调用总次数固定。小任务短超时——卡住了快速失败释放 Worker，不堵队列；大任务长超时——不被误杀。

> **面试话术：** 超时不是全局一刀切，按链路角色分两类处理。接入层跟业务内容无关，写死固定值。执行层单次调用靠压测定最坏值，总超时根据实际页数动态计算——小任务短超时早失败早释放，大任务长超时不被误杀。


### 4.2 队列背压与 ETA 预估

#### 背压三档机制

无背压 → 流量涌入 → 队列无限堆积 → Redis 内存打满 → 服务雪崩。

由于 VL 是唯一瓶颈，系统仅以 `vl_tasks` 队列长度作为背压判断依据（LLM 和音频队列配额充足几乎不堆积），简化实现：

- VL 队列 < 200 → 正常接收，返回 202
- VL 队列 200~500 → 正常接收，前端展示预计等待时间预警
- VL 队列 ≥ 500 → 直接拒绝，返回 503

中间档的核心意图：不是"满了才说"，而是**提前让用户感知压力**。用户看到等待时间自己决定排不排，比系统粗暴关门体验好得多。最后一档是系统底线——保护已在队列中的任务不受影响。

#### ETA 精准预估

摒弃"队列位置 × 20 秒"的粗糙公式，基于 VL 队列中排队任务的实际页数逐任务累加：

```
单任务预估耗时 = 页数 × VL 单次最坏值 + 分类 LLM（1次） + max(三维度并行) + 汇总 LLM（1次）
总等待时间 = 前方所有排队任务预估耗时之和
```

页数在任务创建时已知（PPT 转 PNG 即确定），LLM 三维度为并行执行取最长维度而非相加。数值不需要精确到秒，但比一刀切方案可信度高得多——页数多的任务耗时长、页数少的耗时短，用户看到的不是虚构的固定值。

> **面试话术：** 背压分三档——正常接收、预警提示、拒绝保护。因为 VL 是唯一瓶颈，只监控 VL 队列长度，简化实现。ETA 不是简单乘固定值，而是把前方每个任务的实际页数代入计算，用户看到等待时间可以自己决定排不排。


### 4.3 数据库读写分离

配了两个 SQLAlchemy 引擎——`write_engine` 连主库，`read_engine` 连从库。评分结果入库走 `WriteSession`，用户查历史记录走 `ReadSession`。调用方不感知背后连的是哪个库。从库通过 PostgreSQL 流复制同步，有几百毫秒延迟，对本业务（提交评分后看的是实时报告不是立刻翻历史记录）影响可忽略。


### 4.4 鉴权设计

双通道鉴权：内网 IP 自动识别走免密登录，外网走 JWT 用户名密码登录。`/api/analyze` 接口做了**可选鉴权**——JWT 解析失败不抛异常，返回 None。登录用户提交后评分记录自动绑定账号；未登录用户照样能用，只是不写历史记录。内部工具的核心是降低使用门槛，不是强制注册。

免密登录的本质是"设备即账号"模式：设备首次访问时服务端生成 UUID 作为长期身份标识，存入 HttpOnly Cookie（10 年有效期，JS 不可读，防 XSS）。用户无感知完成"注册+登录"，二次打开直接是登录态。


### 4.5 SSE 流式进度推送

为什么用 SSE 而不是 WebSocket？评分任务耗时数分钟。如果前端轮询（每 2 秒 GET 一次），200 个并发用户就是每秒 100 次无效请求。SSE 是 HTTP 长连接，后端主动推送，前端一个连接接收全部进度事件。选择 SSE 而非 WebSocket 因为评分进度只需**单向推送**——后端推数据给前端，前端不需要发消息给后端。SSE 比 WebSocket 更轻量，浏览器原生支持自动重连。

## 五、自动化测试验证体系

### 5.1 合约测试（配置漂移防护）

成本最低、收益最高的防线。把所有跟 API 配额绑定的配置值写死为断言，CI 每次 push 跑，5 秒完成，零外部依赖：

| 被测项                  | 期望值     | 变更后果         |
| ----------------------- | ---------- | ---------------- |
| VL 令牌桶 rate          | 1.0        | 改了就 429       |
| LLM 令牌桶 rate         | 20.0       | 改了就 429       |
| VL Worker 并发          | 1          | 开多超配额       |
| LLM Worker 并发         | 20         | 开少浪费配额     |
| 熔断器 VL fail_max      | 5          | 太敏感/太迟钝    |
| 熔断器 VL reset_timeout | 60         |                  |
| 降级链层数（VL）        | 4 层       | 少一层少一种容灾 |
| VL 降级链末层           | skip_image | 不能是抛异常     |
| 队列接收/拒绝阈值       | 200 / 500  |                  |
| VL 单次调用超时         | 30s        |                  |
| LLM 单次调用超时        | 60s        |                  |

防止任何人"不小心改了一个数字"导致上线触发 429。

### 5.2 令牌桶并发安全测试

**测试方案：** 使用 fakeredis（支持 Lua 的内存 Redis，无需容器，单测几十毫秒，接入 CI）。设计两个核心场景：

1. **空桶高并发争抢**：先耗尽桶内令牌，1000 个协程同时调用 `acquire`，断言成功数为 0。验证 Lua 原子性保证空桶不会超发。
2. **多 Worker 共享配额**：模拟 3 个 Worker 各自尝试 10 次获取，断言总成功数不超过 rate。验证分布式共享桶时全局配额不被突破。

**验证结论：** 场景一通过 → Lua 原子性成立；场景二通过 → 多 Worker 共享配额正确。两个场景过了，限流器核心正确性就立住了——未来扩多少 Worker 都不会突破全局配额。

> **面试话术：** 令牌桶用 fakeredis 做了并发安全测试，两个核心场景：1000 协程抢空桶断言零成功、多 Worker 共享桶断言总成功数不超配额。这两个过了，限流器就稳了，扩多少 Worker 都不会突破全局配额。

### 5.3 熔断器 + 降级链自动化验证

**测试方案：** 全部 Mock，不调真实 API，不产生费用。熔断器用 pybreaker 自带状态查询接口验证状态流转。降级链用 respx 在 HTTP 层拦截请求，模拟不同层级故障。

**熔断器验证点：**

- 连续 5 次失败 → 触发熔断，第 6 次抛 `CircuitBreakerError` 且 API 调用次数未增加（证明 OPEN 态根本不发请求）
- 冷却过后进入 HALF-OPEN，只放 1 个探测请求；成功回 CLOSED，失败回 OPEN

**降级链验证点：**

- 主模型故障 → 自动切降级 1；前两层均故障 → 自动切降级 2
- 全部故障 → 触发兜底，返回默认结果而非抛异常

> **面试话术：** 熔断器和降级链全用 Mock 测试，不花一分钱。熔断器测完整状态机的每条流转边，重点断言熔断态下 API 调用次数不增加——证明真的没发请求。降级链测不同层级故障下的切换顺序和兜底行为。容灾逻辑上线前必须全自动化验证。

### 5.4 三段式流水线吞吐验证

**测试方案：** Mock 所有外部 API（VL 单页 1s、LLM 单次 3s），Celery 三段队列与令牌桶真实运行。10 个用户并发提交 20 页 PPT，每个阶段打时间戳，通过时间轴数据验证架构设计。

**三个核心断言：**

1. **VL 严格串行**：相邻用户的 VL 时间段无重叠，验证令牌桶 + 单 Worker 串行生效
2. **三段解耦生效**：用户 A 的 LLM 时间段与用户 B 的 VL 时间段存在重叠，验证无空转
3. **吞吐符合理论值**：总耗时 = 10 × 20s = 200s，偏差在 ±15% 以内，无额外串行阻塞点

**验证结论：** 三个断言全部通过，三段式解耦确实消除了瓶颈串行带来的资源空转——架构图不是画出来的，是跑数据验证出来的。
